# CIP-0010: GPy2 readiness — modernise GPy1, deprecate what will not carry forward, define the upgrade contract

## Status

- [x] Proposed - Initial idea documented (open for Discussion feedback)
- [ ] Accepted - Approved, ready to start work
- [ ] In Progress - Actively being implemented
- [ ] Implemented - Work complete, awaiting verification
- [ ] Closed - Verified and complete
- [ ] Rejected - Will not be implemented
- [ ] Deferred - Postponed

## Summary

This CIP is about **GPy1**: the work that should happen in the current
codebase so that, when a successor exists, upgrading is easy and
verifiable. The design of that successor (provisionally "GPy2") is **out
of scope** and belongs in its own CIP.

It is an umbrella for work already under way in narrower CIPs (CIP-000E
Cython, CIP-000F paramz, CIP-0002 tying, CIP-000B visualize, CIP-000D
kernel coverage) and adds five things none of them cover alone:

1. **A deprecation policy and a mechanism that actually reaches users.**
2. **An upgrade contract:** a recorded inventory of the GPy1 public API
   that a successor compatibility layer must honour.
3. **A golden-value corpus:** GPy1 outputs for canonical models, used as
   GPy1 regression tests now and as successor parity tests later.
4. **Forward-compatible habits in GPy1:** serialisation coverage, explicit
   random number generators, documented shape conventions, pure numerical
   functions — and, if Accept agrees, a custom-kernel path that only
   requires `K`/`Kdiag`.
5. **Transformation-readiness and successor-API investigation:** evidence
   from CIP-000F Stage 2 / 2T / 2N and Workstreams G–H about functional
   transformations, posterior state, covariance-operation boundaries and
   dual APIs — so a successor backend and model architecture are chosen
   from evidence rather than imitating any one peer framework.

Appendix A records design lessons from GPyTorch, GPflow, GPJax and others
as inputs to the successor CIP. Organising stance: learn from all three;
imitate none. This CIP acts on the ones GPy1 can act on now.

Community review: [Discussion #1297](https://github.com/SheffieldML/GPy/discussions/1297)
(Ideas; same pattern as CIP-000E / [#1279](https://github.com/SheffieldML/GPy/discussions/1279)).

### Assumptions (working hypotheses for this CIP)

These are **assumed** so GPy1 work can proceed; they are not GPy2 design
decisions. If Discussion rejects any of them, this CIP's contract changes
shape and should be revised before Accept.

| Assumption | Implication for GPy1 |
|---|---|
| Successor ships under a **separate package / import name** (side-by-side install) | Deprecations warn; they do not remove working 1.x APIs |
| Migration format for saved models is **`to_dict` / versioned JSON**, not pickle | Extend and freeze JSON serialisation in GPy1 |
| Upgrade claim is checked by a **recorded golden corpus** (mathematical parity within tolerances, not bit-identity) | Build the corpus and tolerances in GPy1 CI now |

**Not assumed here** (belongs in the GPy2 design CIP): which numerical
backend or execution model the successor adopts, module layout, whether
GPy1 eventually re-exports or redirects, approximate inference redesign,
linear-operator kernels. JAX may be evaluated experimentally under
Workstream G / CIP-000F Stage 2T; that evaluation does **not** commit GPy 2
to JAX.

### Organising principle

GPy 2 should learn from GPyTorch, GPflow and GPJax, but should **not simply
imitate any one of them**. The modernisation of GPy 1 exists **not to imitate
modern frameworks, but to discover which architectural abstractions are worth
preserving in the successor, using existing GP algorithms as the test cases.**

Three standout lessons (detail in Appendix A):

1. **From GPyTorch:** numerical linear algebra should be a first-class
   abstraction, not buried inside inference implementations.
2. **From GPflow:** automatic differentiation can greatly simplify a GP
   library, but tightly coupling the library to a large execution framework
   has long-term costs.
3. **From GPJax:** pure functional programming is valuable, but the design of
   model composition, parameter handling and posterior conditioning matters
   just as much as the choice of JAX.

A fourth, shared lesson: treat numerical correctness, differentiation, shape
semantics and performance as architectural concerns from the beginning,
rather than things to address after porting algorithms.

Attractive direction for a successor (decision deferred to the GPy 2
architecture CIP): a mathematically explicit GP library with functional
numerical kernels, well-defined posterior states, structured linear-algebra
interfaces and a coherent parameter model, implemented on a deliberately
chosen backend.

### Design principle — Evidence before backend selection

**Central framing:** use JAX as a **test of GPy's architectural assumptions**
before using it as the foundation of GPy 2. GPy 1 remains a NumPy/SciPy
library; CIP-000F Stage 2 / 2T / 2N refactor the numerical core toward
functional transformations and treat JAX as a diagnostic target, not a
premature backend commitment.

GPy 2 should not select its numerical backend solely on the basis of API
similarity, existing ecosystem popularity or anticipated accelerator
performance.

The choice should be informed by experiments with representative GP
algorithms, undertaken during GPy 1 modernisation (CIP-000F Stage 2 / 2T
and Workstream G below).

In particular, we distinguish:

1. **Mathematical semantics:** GP models, kernels, likelihoods and
   inference objectives.
2. **Numerical implementation:** matrix operations, factorisations, solves
   and approximation methods.
3. **Execution semantics:** mutation, differentiation, compilation,
   batching and device execution.
4. **User-facing modelling API:** model construction, parameter management,
   optimisation and prediction.

These concerns need not all be coupled to the same software abstractions.

A future GPy 2 may adopt JAX as its primary backend, but this should follow
from an explicit decision about the desired execution model rather than an
assumption that JAX is a drop-in replacement for NumPy. Array-API
resemblance ("JAX-compatible NumPy code") is not the same as algorithms that
compose under transformations ("JAX-compatible algorithms"); some procedures
will need different formulations. Workstream G exists to surface that gap.

### Minimal readiness bar (when this CIP may be Implemented)

CIP-0010 closes on **owned deliverables**, not on finishing every related
CIP. Mark **Implemented** when all of the following are true:

1. Deprecation policy shipped: helper, `DEPRECATIONS.md`, global
   `DeprecationWarning` filter removed (with narrow third-party filters if
   needed).
2. Public API inventory script + checked-in snapshot + CI diff.
3. Golden corpus **first pass** (see Workstream C) in CI with recorded
   tolerances.
4. `to_dict` / `from_dict` round-trips for that same first-pass set;
   JSON schema versioned.
5. Migration docs skeleton under `docs/migration/`.
6. A representative **transformation-readiness assessment** has been
   completed using pure numerical functions extracted from GPy 1 (see
   Workstream G). The assessment records numerical parity, gradient
   parity, transformation compatibility and outstanding architectural
   constraints. Its findings are available to inform the GPy 2
   architecture proposal.

   **Default scope for this criterion (keep it small):** one exact GP
   example (RBF log marginal likelihood), followed by one sparse
   variational example, with barriers documented. That pair should surface
   critical architectural issues without making an extensive JAX experiment
   programme a hard prerequisite for GPy 2 planning. It does **not**
   require completion of a JAX port, full CIP-000F Stage 2 coverage, or
   further cases from the Stage 2T backlog (psi-statistics, Bayesian
   GPLVM, …) — those remain optional follow-ons.

Child CIPs keep ownership of their own outcomes. Each should record that
it **feeds CIP-0010** (via `related_cips`) without waiting on this umbrella
to close — and this CIP does not re-decide their Accept questions.

Corpus expansion, remaining deprecations after Discussion, and full
inventory `to_dict` coverage are backlog after the readiness bar, not
blockers for Implemented.

## Motivation

- **Upgrade ease is the main constraint on a successor.** GPy's users have
  scripts, saved models, custom kernels and published tutorials. A GPy2
  that is technically better but expensive to adopt splits the community.
  Most of what makes an upgrade easy has to be prepared in GPy1: you
  cannot write a parity test against outputs nobody recorded, or load
  models in a format nobody can export.
- **Importing GPy re-silences enabled deprecation warnings.**
  `GPy/__init__.py` used to call
  `warnings.filterwarnings("ignore", category=DeprecationWarning)` at
  import time. CPython already ignores `DeprecationWarning` by default;
  the harm was that GPy **re-installed** that ignore after users had
  turned warnings on (`python -Wd`, `PYTHONWARNINGS=default`), hiding
  GPy's own deprecations and third-party ones for the whole process.
  Fixed in [PR #1298](https://github.com/SheffieldML/GPy/pull/1298).
  User-facing GPy deprecations should still use `FutureWarning` (visible
  by default); some call sites already do (e.g. priors). House style:
  one category and one helper.
- **Some code cannot run at all.** `kern/src/psi_comp/ssrbf_psi_comp.py`
  tries `from scipy import weave` (removed from SciPy years ago) and
  `defaults.cfg` still has a `[weave]` section. The state-space Cython
  module never loads (CIP-000E). Dead paths cost reviewers' time and
  coverage.
- **Several features may not carry forward and users should hear early.**
  MPI and PyCUDA paths, paramz internals exposed through GPy, and code
  already marked dead by CIP-000D are **candidates for Discussion**, not
  decisions. Users who rely on any of them should find out from GPy1
  warnings and from [Discussion #1297](https://github.com/SheffieldML/GPy/discussions/1297),
  not from a successor release.
- **Custom kernels are high-leverage.** For many power users, upgrade cost
  is custom kernels and likelihoods, not `GPRegression`. Preparing a
  GPy1 path that only requires forward functions is part of readiness,
  not an afterthought.
- **The narrower CIPs need a shared frame.** CIP-000E and CIP-000F both
  cite "a future GPy2" as motivation. This CIP states what that means for
  GPy1 so each of them can be judged against it.
- **Backend choice needs evidence, not resemblance.** A NumPy-like array
  API does not imply that GP algorithms will compose under differentiation,
  JIT or vectorisation. CIP-000F Stage 2 / 2T extracts pure numerical
  functions and probes transformations experimentally; Workstream G turns
  those findings into a report that informs (but does not decide) the
  successor architecture.

## Detailed Description

### Workstream A — Deprecation policy and mechanism

**Policy (proposed):**

| Rule | Detail |
|---|---|
| Nothing user-facing is removed during 1.x | Deprecated features keep working in GPy1; they are simply not carried into the successor. |
| Exception: code that cannot run | Dead paths (e.g. `scipy.weave`) may be removed in a minor release with a CHANGELOG entry. |
| Warnings are visible | User-facing deprecations use `FutureWarning` (shown by default), not `DeprecationWarning`. Existing `DeprecationWarning` call sites migrate to the helper. |
| Every deprecation names a replacement | Either a GPy1 alternative or "not carried into GPy2; see CIP-0010". |
| One helper | `GPy.util.deprecation.deprecated(...)` decorator/function so wording, category and tracking are consistent. |
| Tracked | Each deprecation is listed in a `DEPRECATIONS.md` table (feature, version deprecated, replacement, GPy2 status). |

**First action (measured PR):** remove the global `DeprecationWarning`
filter from `GPy/__init__.py` —
[PR #1298](https://github.com/SheffieldML/GPy/pull/1298). Probe on import
plus a simple `GPRegression` fit showed no third-party
`DeprecationWarning` flood, so no narrow filters were needed in that PR.
Remaining user-visible messaging is the `FutureWarning` house style
below, not relying on `-Wd`.

**Candidate list (for Discussion — not decided here):**

| Feature | Evidence | Proposed GPy1 action | Successor status (provisional) |
|---|---|---|---|
| `scipy.weave` path, `[weave]` config | Cannot import on any supported SciPy | Remove (dead code) | Not carried |
| State-space Cython import | Never loaded; extension removed (CIP-000E Phase 2) | Done on `cip000E-numpy-blas-primitives` (merge pending) | Redesign only if state-space is retained (Option D deferred) |
| MPI: `core/sparse_gp_mpi.py`, `var_dtc_parallel`, `util/parallel.py` | Optional `mpi4py`; low visibility in tests | Deprecate (FutureWarning) if Discussion confirms | Sharding / other, if needed |
| GPU psi-statistics: `rbf_psi_gpucomp`, `ssrbf_psi_gpucomp`, `util/linalg_gpu.py`, `util/gpu_init.py` | Optional PyCUDA/scikit-cuda; excluded from coverage (CIP-000D) | Deprecate if Discussion confirms | GPU via successor stack |
| paramz internals re-exported by GPy (`ObsAr`, index operations) | CIP-000F Stages 0–3 | Deprecate as each stage lands | Not exposed |
| `tie_to` (documented, not implemented) | CIP-0002 | Document as unavailable | Designed into successor parameter tree |
| `lfm1` and other kernels marked dead | CIP-000D | Per CIP-000D | Not carried unless requested |
| matplotlib `visualize` | CIP-000B | Per CIP-000B | Replaced by CIP-000B explorer |
| Cython extensions | CIP-000E Accept Option C → Phase 2 toward A | **Removed on branch** `cip000E-numpy-blas-primitives` (pure NumPy/BLAS defaults; merge pending). Small helpers still slower than former Cython; packaging win accepted | Successor does not ship these Cython modules. A future design may still need *some* compiled kernels (not necessarily Cython); do not treat "no compiled code ever" as settled. |
| `GPy.inference.mcmc` (HMC, samplers) | Small; superseded elsewhere | **Discuss** | Possibly external sampler integration |
| `GPy.util.datasets` downloaders | External URLs; maintenance cost | **Discuss** | **Discuss** |

### Workstream B — Upgrade contract (API inventory)

Record, in the repository, the public surface that a successor
compatibility layer must support.

**Definition of "public" for the inventory** (needed because GPy's surface
is largely accidental):

A name is **public** if any of the following holds:

1. It is listed in a module `__all__`, or
2. It is a user-facing class under `GPy.models`, `GPy.kern`,
   `GPy.likelihoods`, `GPy.mappings`, or documented inference entry
   points, and appears in Sphinx / tutorial docs, or
3. It is an attribute or method named in the behavioural checklist below
   (`optimize`, `predict`, `to_dict`, regex indexing, …).

Private helpers, test-only symbols, and undocumented underscore-prefixed
names are out of scope for the compatibility checklist. The inventory
script should encode this rule and document exceptions in the checked-in
file header.

**Inventory contents:**

- Public names under the modules above, with constructor signatures and
  defaults.
- Parameter names and default constraints per kernel and likelihood
  (e.g. `rbf.variance`, `rbf.lengthscale`, `Logexp`).
- Model-level behaviours users depend on: `optimize()` (default optimiser
  and options), `optimize_restarts`, `predict` / `predict_quantiles` /
  `posterior_samples_f` return shapes, `print(m)` table layout, regex
  indexing `m['.*lengthscale']`, `constrain_*` / `fix` / `set_prior`,
  `to_dict` / `save` / `load`.

Generated by a script (`scripts/api_inventory.py`) into a checked-in file,
with a CI job that diffs it so API changes are visible in review. The
inventory is also the checklist for the successor compatibility layer.

Supplement with Discussion #1297: which models, kernels and features do
you actually use, and do you maintain custom kernels or likelihoods?

### Workstream C — Golden-value corpus

A set of canonical models with fixed data and seeds, and recorded outputs:
log-likelihood and gradient at fixed parameters, optimised parameters,
predictions (mean, variance, quantiles) at fixed test points.

**Parity claim (decide at Accept):** mathematical agreement within stated
tolerances — not bit-identity across BLAS / JAX. Split each case into:

- **Value parity** at fixed parameters (LL, gradients, predict).
- **Optimise parity** where useful (comparable LL / parameters within
  looser tolerances), recorded separately so platform noise does not fail
  the fixed-parameter oracle.

Platform and dependency versions (NumPy, SciPy, BLAS) are stored in the
JSON metadata next to each artefact.

**First pass (readiness bar — ship in CIP-0010):**

- `GPRegression`: RBF ± ARD, one Matérn, one sum or product
- One sparse regression model
- One classification path (Laplace *or* EP — Discussion may prefer one)
- One latent-variable model (`BayesianGPLVM` or simpler GPLVM)

**Expansion (backlog after readiness bar; builds on CIP-0009 / CIP-000D):**

`SVGP`, `MRD`, `GPCoregionalizedRegression`, the other classification
path, one state-space model, additional non-Gaussian likelihoods.

- In GPy1 the corpus is a regression suite: refactors from CIP-000E/000F
  must not move these numbers beyond stated tolerances.
- For the successor it is the parity suite: the upgrade claim is "these
  numbers match within tolerance".
- Stored as small `.npz` plus JSON metadata (tolerances, GPy version,
  NumPy/SciPy versions).

### Workstream D — Serialisation as the migration path

A successor cannot be assumed to unpickle GPy1 objects. The migration path
for saved models is `to_dict` (JSON), which today is implemented in 9
model/core modules.

- **Readiness bar:** `to_dict` / `from_dict` for every model in the
  **first-pass corpus**, schema version frozen.
- **After bar:** extend to every inventory model, or explicitly mark
  unsupported in the inventory.
- Document "convert your pickles under GPy1: `GPy.load` → `m.to_dict()` →
  file".
- Version the JSON schema so a successor `from_gpy1()` loader has a
  stable target.

### Workstream E — Forward-compatible numerical habits

- **Pure numerical functions** for kernels and likelihoods: CIP-000F
  Stage 2. These become successor port targets and the pattern
  custom-kernel authors look for.
- **Custom-kernel helper (elevated — resolve at Accept):** a GPy1 base
  class (or helper) where authors implement only `K` / `Kdiag`; GPy1
  obtains gradients by finite differences (or existing autodiff-free
  machinery). Goal: custom kernels written in the shape the successor
  will need, *before* the successor exists. Same idea for likelihoods
  (`logpdf` first) if scope allows.
- **Explicit random number generators:** ~108 direct `np.random.*` calls
  outside tests/examples. Accept an optional `rng`
  (`np.random.Generator`) wherever randomness is used (initialisation,
  restarts, sampling). Maps onto explicit PRNG keys in a functional
  successor.
- **Shape conventions documented:** one page that states GPy's conventions
  (X: N×Q, Y: N×D, multi-output index columns, variance shapes returned
  by `predict`), with shape assertions in tests. Successor adopts the
  same conventions so scripts keep working.
- **No new hand-coded-gradient-only features:** new kernels and
  likelihoods should implement the pure forward function first; hand
  gradients are added for GPy1 only.

Optional GPy1 APIs shaped like a successor posterior protocol
(`posterior(X)` with mean / variance / sample) are **open question 4** —
not required for the readiness bar.

### Workstream F — Migration documentation (started in GPy1)

- `docs/migration/` skeleton: what is deprecated and why, how to convert
  saved models, how a custom kernel looks as pure `K`/`Kdiag` functions.
- Grows as Workstreams A–E land; becomes the successor migration guide.

### Workstream G — Transformation-readiness assessment

Use the pure numerical functions and experimental implementations developed
under [CIP-000F](cip000F.md) Stage 2 / 2T to investigate the suitability of
functional program transformations for core GP algorithms.

JAX began with a NumPy-like interface but necessarily departed from NumPy
semantics to support transformations such as automatic differentiation, JIT
compilation and vectorisation. Backend compatibility for a successor cannot
be established merely through interchangeable array APIs. This workstream
records what GPy 1 modernisation learns about that gap — without deciding
that GPy 2 must use JAX or support multiple numerical backends.

The assessment should address:

**Functional semantics**

- Can objectives and predictions be expressed without hidden mutable state?
- Which model components must be static during compilation?
- Which parameters, inputs and variational quantities can remain dynamic?
- How should parameter tying, constraints and shared parameters be
  represented?

**Numerical computation**

- Can existing analytical gradients be reproduced by automatic
  differentiation?
- Where are custom derivative rules preferable?
- Which factorizations or structured linear algebra operations need
  specialised implementations?
- Does JIT compilation materially improve performance?
- Which operations benefit from vectorisation or batching?
- Dense versus operator-based covariance calculations (CIP-000F Stage 2N)?
- First- and **second-order** differentiation where meaningful (do not
  assume higher-order correctness follows from first-order autodiff —
  GPyTorch's ongoing derivative/broadcasting fixes are a warning)?

**Compatibility**

- Can the existing GPy public API wrap the extracted numerical functions?
- Which behaviours rely on mutable parameter objects or implicit cache
  invalidation?
- Could a successor preserve familiar model construction while changing
  internal execution semantics?
- Which compatibility guarantees are meaningful, and which would constrain
  the successor unnecessarily?

**Dependency and differentiation boundary** (lesson from GPflow)

- How much handwritten derivative code could genuinely be removed?
- Which analytical derivatives should remain as correctness references?
- Which custom derivative rules improve stability or performance?
- How deeply would parameters and models depend on the chosen autodiff
  framework?
- What happens when that framework changes its array, transformation or
  module APIs?
- Autodiff does **not** replace numerical expertise: the GP library still
  owns inference correctness (e.g. silent Cholesky failures).

**Performance**

- Compare equivalent precision and numerical algorithms.
- Measure compilation overhead separately from repeated execution.
- Measure peak memory, runtime and gradient evaluation cost.
- Include small and medium-sized GP problems as well as representative
  sparse models.
- Comparison of single- and double-precision numerical behaviour.
- Repeated prediction using explicit posterior state (`ConditionedState`).
- Preserve NumPy/SciPy implementations as baselines.

**Experimental probes for JAX (or other) ports** under this workstream:

- Numerical and gradient equivalence with existing GPy implementations.
- First- and second-order differentiation where meaningful.
- Batching and broadcasting across model inputs and parameters.
- Dense versus operator-based covariance calculations.
- Repeated prediction using explicit posterior state.
- Single- vs double-precision behaviour.
- Compilation costs versus repeated execution costs.

**Deliverable — Transformation-readiness report.** A concise report
summarising:

- Successfully extracted pure numerical components.
- Numerical and gradient parity results.
- JIT and vectorisation compatibility.
- Architectural barriers discovered (using the CIP-000F Stage 2T
  classification).
- Cases where JAX transformations offer measurable benefits.
- Cases where backend-specific approaches remain preferable.
- Findings on `CovarianceOperator` / `ConditionedState` / `ParameterSpec`
  (CIP-000F Stage 2N).
- Implications for GPy 2 model architecture and backend selection.

The report informs a subsequent GPy 2 architecture CIP. It does **not**
decide that GPy 2 must use JAX.

**Preferred experimental sequence** (each experiment should yield a
*decision*, not merely another model port):

| # | Experiment | Informs |
|---|---|---|
| 1 | Exact GP — pure NumPy LML, posterior state, predictions; JAX parity | State separation; transformation readiness |
| 2 | Sparse GP — SVGP or collapsed sparse with inducing points, constraints, posterior state | Parameter structure; operators; autodiff |
| 3 | Non-Gaussian — Laplace or EP; analytical vs automatic derivatives | Whether the architecture accommodates multiple inference paradigms |
| 4 | Bayesian GPLVM — latents, psi-statistics, joint optimisation, batching | Complex-model stress test |

**Readiness bar** still only requires experiments **1 and 2** (see criterion
6). Experiments 3–4 strengthen the GPy 2 architecture CIP and should not
block CIP-0010 Implemented. Do **not** silently drop Laplace / EP (or other
historically supported methods) merely because peer frameworks emphasise
SVGPs — breadth is a scientific asset; port decisions should follow usage,
mathematical value and maintenance cost.

**Suggested first experiment** (owned as implementation under CIP-000F
Stage 2 / 2T / 2N; findings land here): extract the exact GP regression log
marginal likelihood as a pure NumPy/SciPy function with the existing GPy
interface as a wrapper; condition once into explicit numerical state;
predict repeatedly from that state; verify parity; assess a separate JAX
equivalent under `jax.grad` / `jax.jit`; record barriers. Completion means
useful evidence, not perfect JAX compatibility.

### Workstream H — Successor API investigation (dual interface)

Test separation between the mathematical model, learned parameters,
conditioning and the posterior — **without changing GPy 1's public API**.

Particularly useful experiment: express the same exact GP regression problem
through two interfaces sharing one numerical core:

1. Existing GPy model API (`GPRegression` → `optimize` / `predict`).
2. A functional model / condition / posterior API (inspired by GPJax 1.0's
   conditioning-centred design).

Evaluate whether the new abstraction improves composability, transformation
compatibility and reuse without sacrificing GPy's familiar ergonomics.
Today's `optimize()` / `predict()` conflate model, fitted parameters,
posterior representation and training algorithm; making those explicit
internally may reveal that observer caching largely compensates for a
missing posterior-state abstraction (see CIP-000F Stage 2N / Stage 3).

**Dependency containment:** keep any experimental functional API free of
direct dependence on a particular parameter-management library's concepts
(Flax NNX, Equinox, paramax, …). GPJax's own module churn shows that even
JAX-native stacks evolve; mathematics should stay stable across that churn.

Findings feed the transformation-readiness report and the future GPy 2
architecture CIP. Not a readiness-bar blocker beyond what criterion 6
already requires from experiments 1–2.

**Evidence already available from CIP-000E (2026-11-16).** Before Stage 2T
experiments start, record what Cython → NumPy/BLAS replacement already showed
(full write-up in [CIP-000E](cip000E.md); harness
`benchmarks/cip000E/`):

- **Pure hot-path primitives exist** and beat or match Cython on the
  dominant costs (Murray Cholesky VJP at N≳1000; stationary lengthscale /
  ``gradients_X``; coregionalize reduce). SparseGP end-to-end is
  parity-or-better on Mac/Accelerate.
- **Array rewrite ≠ numerical identity.** Expanded BLAS forms need shared
  mean-centring under large common offsets; blocked Cholesky needs an
  unblocked VJP on updated diagonal blocks. These are exactly the class of
  barriers Workstream G should catalogue (formulation / precision), not
  “JAX vs NumPy API” issues.
- **Small helpers can remain slower** (`symmetrify`, triang maps,
  coregionalize ``K`` on Accelerate) while still justifying dropping a
  compile surface — packaging and maintenance are first-class readiness
  inputs, not only wall-clock.
- **JAX was not required** to Accept or execute CIP-000E. Keep that
  separation when scoring Stage 2T experiments.

### Non-goals

- Choosing the successor's frameworks, module system or package layout
  (separate GPy2 CIP; Appendix A and Workstreams G–H record inputs).
- Committing GPy 2 to JAX (or to multi-backend support) before a successor
  architecture CIP reviews the evidence via a **backend decision record**
  (see below).
- Introducing JAX or any autodiff dependency into the GPy1 *runtime*
  (experimental JAX code under CIP-000F Stage 2T may live outside the
  package dependency graph).
- Completing a full JAX port of GPy1.
- Adopting GPyTorch's entire linear-operator architecture in GPy 1.
- Adopting a whole JAX module ecosystem as part of any public modelling API.
- Discarding GPy's analytical inference implementations / gradients in
  favour of autodiff everywhere (retain as mathematical references).
- Silently abandoning Laplace, EP or other historically supported methods
  solely because peer libraries emphasise variational sparse GPs.
- Removing working user-facing features during 1.x.
- Re-deciding questions owned by CIP-000E, CIP-000F, CIP-0002, CIP-000B or
  CIP-000D; this CIP only records how their outcomes feed readiness.
- Waiting for full Cython / paramz retirement before marking this CIP
  Implemented.

### Input to the future GPy 2 architecture CIP — Backend decision record

Before choosing JAX or another backend, the successor architecture CIP
should require a short comparative design record addressing:

- Compatibility with the desired model and posterior abstractions.
- Support for the required inference algorithms (including non-variational
  methods GPy historically ships).
- Numerical linear algebra and custom derivative requirements.
- Compilation, batching and device execution.
- Dependency footprint and long-term maintenance.
- Migration cost for existing GPy users.

That record must be supported by CIP-000F and CIP-0010 experiments, not by
broad claims about framework performance.

### Shared implementation guidance

Shared with [CIP-000F](cip000F.md) Stage 2 / 2T:

1. **Improve GPy 1 first.** Production changes need an independent
   justification in correctness, testability, maintainability, performance
   or clarity — not JAX compatibility alone.
2. **Preserve analytical gradients** as references (and potential custom
   rules); evaluate autodiff against them.
3. **Do not introduce a universal array or operator abstraction
   prematurely**; let Stage 2N / Workstream G show which protocols are
   reusable. Preserve flexibility in mathematical operations without
   copying GPyTorch's full hierarchy into GPy 1.
4. **Separate production and experimental environments**; no JAX runtime
   dependency for GPy 1.
5. **Treat incompatibilities as findings**, not as mandates to rewrite
   production algorithms until every transformation test passes.
6. **Keep GPy 2's architectural choice open**; evidence, not de facto
   commitment. Public APIs should not depend on a particular
   parameter-management library's concepts.
7. **Retain independent numerical oracles** (analytical gradients, golden
   corpus); autodiff and framework ops are not substitutes for owning
   inference correctness.

### Alternatives considered

| Option | Verdict |
|---|---|
| Umbrella readiness CIP coordinating existing CIPs (this CIP) | Preferred |
| Fold everything into a single GPy2 design CIP | Mixes GPy1 maintenance with undecided successor design; blocks useful GPy1 work on design debates |
| Separate CIP per workstream only | Loses the shared frame; deprecation policy and upgrade contract need one owner |
| Start the successor without GPy1 preparation | No parity oracle, no migration format, users surprised by dropped features |

## Backward Compatibility

- No working user-facing feature is removed during 1.x; deprecated
  features warn with `FutureWarning`.
- Removing the global `DeprecationWarning` filter does not change the
  default interactive experience (CPython still ignores
  `DeprecationWarning` unless enabled). It stops GPy from undoing
  `-Wd` / `PYTHONWARNINGS=default`. Release notes for PR #1298 say so;
  narrow third-party filters were unnecessary in that change.
- Adding optional `rng` arguments is backward compatible (default keeps
  current behaviour).
- Dead-code removal (`scipy.weave`) changes no behaviour, because the
  code cannot run.

   (See REQ-0003.)

   variance and sampling), or keep GPy1's API frozen and add those only
   in the successor? (Not required for the readiness bar.)
5. **Golden corpus tolerances.** Fixed absolute/relative vs per model?
   How are platform-dependent BLAS differences handled in metadata?
   Default proposal: per-model tolerances; value parity strict;
   optimise parity looser.
6. **Custom kernels (elevated).** Provide a GPy1 helper where users write
   only `K`/`Kdiag` and gradients come from finite differences in GPy1,
   so custom kernels are written successor-style before the successor
   exists?
7. **Transformation-readiness scope for the readiness bar.** Default
   proposal above: exact GP LML **plus** one sparse variational case.
   Confirm at Accept, or shrink to exact-GP-only if Discussion prefers a
   thinner bar before GPy 2 planning starts.

## Appendix A — Design lessons recorded for the GPy2 CIP

Collected from other GP packages (2026-11). Not decided here; listed with
whether GPy1 can act now. **Organising stance:** learn from all three major
Python GP frameworks; imitate none wholesale.

### Priority lessons (strongest recommendations)

| # | Lesson | Source | Act in GPy1 now? |
|---|---|---|---|
| 1 | Separate model, posterior and inference algorithm; conditioning and prediction need explicit numerical semantics | GPJax 1.0 (condition-centred API, Sep 2026) | Yes: Stage 2N `ConditionedState`; Workstream H dual-API probe |
| 2 | Make covariance operations first-class; do not make dense materialisation unavoidable | GPyTorch `LinearOperator`; GPJax / Lineax | Yes: Stage 2N conceptual `CovarianceOperator` only — not a full hierarchy |
| 3 | Retain independent numerical oracles (analytical gradients, golden outputs) | GPflow + all three | Yes: Workstream C; preserve hand gradients as references |
| 4 | Separate parameters from their management system (constraints, tying, static structure) | GPJax + GPflow churn | Partly: CIP-000F Stage 4 Option B; Stage 2N `ParameterSpec` |
| 5 | Treat batching, shapes and precision as API contracts from day one | GPyTorch + GPJax | Yes: Workstream E; Workstream G probes |
| 6 | Keep deployment / ecosystem dependencies contained at the public API boundary | GPflow (TF/Keras/TFP); GPJax (Flax→Equinox/paramax) | Yes: no framework types in public API; backend decision record |

### Additional recorded lessons

| Lesson | Source | Act in GPy1 now? |
|---|---|---|
| Keep the parameter layer independent of any module framework; tag parameters by support and map tags to bijectors separately | GPJax (Flax NNX → Equinox / paramax) | Partly: CIP-000F Stage 4 Option B |
| Kernel matrices as structured linear operators (Kronecker, low-rank + diagonal, iterative solves) | GPyTorch `linear_operator`; CoLA (JAX) | Experimental only in GPy1; full design in GPy2 |
| Operator abstractions move derivative/shape complexity into a shared numerical layer — they do not eliminate it | Recent GPyTorch higher-order / broadcasting fixes | Yes: investigate 2nd-order grads in Workstream G |
| Autodiff shrinks the library but the GP package still owns numerical correctness of inference | GPflow (e.g. Cholesky failure handling in 2.11.2) | Yes: keep analytical references |
| Framework dependence is a long-term maintenance commitment | GPflow TF/Keras/TFP compatibility cycles | Yes: backend decision record; contain deps |
| Do not automatically port every historical inference method; decide by usage, maths value and cost | GPflow's narrower focus vs GPy's breadth | Inventory + Discussion; do not silently drop Laplace/EP |
| Separate the GP, its finite projection, the approximation and the posterior; posterior is itself a GP | AbstractGPs.jl | No; GPy2 internals behind GPy's model classes |
| Minimal posterior protocol (mean, variance, sample with explicit key); pathwise sampling | BoTorch | Optional (open question 4) |
| Shape annotations and checks from day one | GPflow `check_shapes`; GPJax JIT-safe assertions | Yes: Workstream E shape conventions |
| State-space kernels declare their SDE form; pure-JAX quasiseparable solvers | tinygp | Partly: GPy's `sde_*` kernels already carry this |
| Functional core with a stateful user-facing layer | tinygp's trade-offs vs george | Workstream H probe; GPy2 compatibility layer |
| Clear package boundaries (kernels, likelihoods, approximations, temporal) | JuliaGPs ecosystem | Partly: deprecations reduce the surface |
| Variational parameterisation that admits natural gradients | GPJax 1.0 | No; GPy2 design |
| Explicit posterior may cache factorisations without observer invalidation | GPJax 1.0 `condition` | Yes: reframes CIP-000F Stage 3 |
| JIT compile latency must not make small interactive models slow | (GPy-specific risk) | Record small-N benchmarks; Workstream G separates compile vs execute |
| Array-API similarity is not transformation compatibility; evidence before backend choice | JAX history vs NumPy | Yes: Stage 2T + Workstream G |
| Separate mathematical, numerical, execution and user-API concerns | (programme framing) | Yes: pure functions in GPy1 |
| Distinguish JAX-compatible NumPy code from JAX-compatible algorithms | (this programme) | Yes: Stage 2T barrier notes |
| Use JAX to test architectural assumptions before adopting it as GPy2 foundation | (this programme) | Yes: diagnostic Stage 2T |

### What not to copy

- **Not** GPyTorch's entire linear-operator architecture into GPy 1 — establish
  the small subset of operations inference actually needs first.
- **Not** the whole JAX module ecosystem as part of the public API — contain
  that boundary (GPJax's Flax / Equinox / paramax churn is the warning).
- **Not** discard analytical inference / gradients for autodiff everywhere —
  retain them as mathematical references even if a successor uses autodiff
  routinely.
