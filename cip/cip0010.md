# CIP-0010: GPy2 readiness — modernise GPy1, deprecate what will not carry forward, define the upgrade contract

## Status

- [x] Proposed - Initial idea documented (open for Discussion feedback)
- [ ] Accepted - Approved, ready to start work
- [ ] In Progress - Actively being implemented
- [ ] Implemented - Work complete, awaiting verification
- [ ] Closed - Verified and complete
- [ ] Rejected - Will not be implemented
- [ ] Deferred - Postponed

## Summary

This CIP is about **GPy1**: the work that should happen in the current
codebase so that, when a successor exists, upgrading is easy and
verifiable. The design of that successor (provisionally "GPy2") is **out
of scope** and belongs in its own CIP.

It is an umbrella for work already under way in narrower CIPs (CIP-000E
Cython, CIP-000F paramz, CIP-0002 tying, CIP-000B visualize, CIP-000D
kernel coverage) and adds four things none of them cover:

1. **A deprecation policy and a mechanism that actually reaches users.**
2. **An upgrade contract:** a recorded inventory of the GPy1 public API
   that a successor compatibility layer must honour.
3. **A golden-value corpus:** GPy1 outputs for canonical models, used as
   GPy1 regression tests now and as successor parity tests later.
4. **Forward-compatible habits in GPy1:** serialisation coverage, explicit
   random number generators, documented shape conventions, pure numerical
   functions — and, if Accept agrees, a custom-kernel path that only
   requires `K`/`Kdiag`.

Appendix A records design lessons gathered so far as inputs to the
successor CIP. This CIP acts on the ones GPy1 can act on now.

Community review: [Discussion #1297](https://github.com/SheffieldML/GPy/discussions/1297)
(Ideas; same pattern as CIP-000E / [#1279](https://github.com/SheffieldML/GPy/discussions/1279)).

### Assumptions (working hypotheses for this CIP)

These are **assumed** so GPy1 work can proceed; they are not GPy2 design
decisions. If Discussion rejects any of them, this CIP's contract changes
shape and should be revised before Accept.

| Assumption | Implication for GPy1 |
|---|---|
| Successor ships under a **separate package / import name** (side-by-side install) | Deprecations warn; they do not remove working 1.x APIs |
| Migration format for saved models is **`to_dict` / versioned JSON**, not pickle | Extend and freeze JSON serialisation in GPy1 |
| Upgrade claim is checked by a **recorded golden corpus** (mathematical parity within tolerances, not bit-identity) | Build the corpus and tolerances in GPy1 CI now |

**Not assumed here** (belongs in the GPy2 design CIP): JAX vs alternatives,
module layout, whether GPy1 eventually re-exports or redirects, approximate
inference redesign, linear-operator kernels.

### Minimal readiness bar (when this CIP may be Implemented)

CIP-0010 closes on **owned deliverables**, not on finishing every related
CIP. Mark **Implemented** when all of the following are true:

1. Deprecation policy shipped: helper, `DEPRECATIONS.md`, global
   `DeprecationWarning` filter removed (with narrow third-party filters if
   needed).
2. Public API inventory script + checked-in snapshot + CI diff.
3. Golden corpus **first pass** (see Workstream C) in CI with recorded
   tolerances.
4. `to_dict` / `from_dict` round-trips for that same first-pass set;
   JSON schema versioned.
5. Migration docs skeleton under `docs/migration/`.

Child CIPs keep ownership of their own outcomes. Each should record that
it **feeds CIP-0010** (via `related_cips`) without waiting on this umbrella
to close — and this CIP does not re-decide their Accept questions.

Corpus expansion, remaining deprecations after Discussion, and full
inventory `to_dict` coverage are backlog after the readiness bar, not
blockers for Implemented.

## Motivation

- **Upgrade ease is the main constraint on a successor.** GPy's users have
  scripts, saved models, custom kernels and published tutorials. A GPy2
  that is technically better but expensive to adopt splits the community.
  Most of what makes an upgrade easy has to be prepared in GPy1: you
  cannot write a parity test against outputs nobody recorded, or load
  models in a format nobody can export.
- **Deprecation warnings do not reach users today.** `GPy/__init__.py`
  calls `warnings.filterwarnings("ignore", category=DeprecationWarning)`
  at import time. This silences GPy's own deprecations (e.g. in
  `core/gp.py`, `util/misc.py`, `core/parameterization/priors.py`) and,
  because the filter is process-wide, other libraries' deprecations for
  anyone who imports GPy. Some call sites already use `FutureWarning`
  (e.g. priors); the house style should be one category and one helper.
- **Some code cannot run at all.** `kern/src/psi_comp/ssrbf_psi_comp.py`
  tries `from scipy import weave` (removed from SciPy years ago) and
  `defaults.cfg` still has a `[weave]` section. The state-space Cython
  module never loads (CIP-000E). Dead paths cost reviewers' time and
  coverage.
- **Several features may not carry forward and users should hear early.**
  MPI and PyCUDA paths, paramz internals exposed through GPy, and code
  already marked dead by CIP-000D are **candidates for Discussion**, not
  decisions. Users who rely on any of them should find out from GPy1
  warnings and from [Discussion #1297](https://github.com/SheffieldML/GPy/discussions/1297),
  not from a successor release.
- **Custom kernels are high-leverage.** For many power users, upgrade cost
  is custom kernels and likelihoods, not `GPRegression`. Preparing a
  GPy1 path that only requires forward functions is part of readiness,
  not an afterthought.
- **The narrower CIPs need a shared frame.** CIP-000E and CIP-000F both
  cite "a future GPy2" as motivation. This CIP states what that means for
  GPy1 so each of them can be judged against it.

## Detailed Description

### Workstream A — Deprecation policy and mechanism

**Policy (proposed):**

| Rule | Detail |
|---|---|
| Nothing user-facing is removed during 1.x | Deprecated features keep working in GPy1; they are simply not carried into the successor. |
| Exception: code that cannot run | Dead paths (e.g. `scipy.weave`) may be removed in a minor release with a CHANGELOG entry. |
| Warnings are visible | User-facing deprecations use `FutureWarning` (shown by default), not `DeprecationWarning`. Existing `DeprecationWarning` call sites migrate to the helper. |
| Every deprecation names a replacement | Either a GPy1 alternative or "not carried into GPy2; see CIP-0010". |
| One helper | `GPy.util.deprecation.deprecated(...)` decorator/function so wording, category and tracking are consistent. |
| Tracked | Each deprecation is listed in a `DEPRECATIONS.md` table (feature, version deprecated, replacement, GPy2 status). |

**First action (measured PR):** remove the global `DeprecationWarning`
filter from `GPy/__init__.py`. Expect noise from paramz / NumPy; ship
**narrow** filters (by module and message) in the **same** change so CI
and early adopters are not flooded. Release notes must say warnings that
were hidden may now appear.

**Candidate list (for Discussion — not decided here):**

| Feature | Evidence | Proposed GPy1 action | Successor status (provisional) |
|---|---|---|---|
| `scipy.weave` path, `[weave]` config | Cannot import on any supported SciPy | Remove (dead code) | Not carried |
| State-space Cython import | Never loads (CIP-000E) | Per CIP-000E | Replaced if state-space is redesigned |
| MPI: `core/sparse_gp_mpi.py`, `var_dtc_parallel`, `util/parallel.py` | Optional `mpi4py`; low visibility in tests | Deprecate (FutureWarning) if Discussion confirms | Sharding / other, if needed |
| GPU psi-statistics: `rbf_psi_gpucomp`, `ssrbf_psi_gpucomp`, `util/linalg_gpu.py`, `util/gpu_init.py` | Optional PyCUDA/scikit-cuda; excluded from coverage (CIP-000D) | Deprecate if Discussion confirms | GPU via successor stack |
| paramz internals re-exported by GPy (`ObsAr`, index operations) | CIP-000F Stages 0–3 | Deprecate as each stage lands | Not exposed |
| `tie_to` (documented, not implemented) | CIP-0002 | Document as unavailable | Designed into successor parameter tree |
| `lfm1` and other kernels marked dead | CIP-000D | Per CIP-000D | Not carried unless requested |
| matplotlib `visualize` | CIP-000B | Per CIP-000B | Replaced by CIP-000B explorer |
| Cython extensions | CIP-000E | Per CIP-000E | Not carried |
| `GPy.inference.mcmc` (HMC, samplers) | Small; superseded elsewhere | **Discuss** | Possibly external sampler integration |
| `GPy.util.datasets` downloaders | External URLs; maintenance cost | **Discuss** | **Discuss** |

### Workstream B — Upgrade contract (API inventory)

Record, in the repository, the public surface that a successor
compatibility layer must support.

**Definition of "public" for the inventory** (needed because GPy's surface
is largely accidental):

A name is **public** if any of the following holds:

1. It is listed in a module `__all__`, or
2. It is a user-facing class under `GPy.models`, `GPy.kern`,
   `GPy.likelihoods`, `GPy.mappings`, or documented inference entry
   points, and appears in Sphinx / tutorial docs, or
3. It is an attribute or method named in the behavioural checklist below
   (`optimize`, `predict`, `to_dict`, regex indexing, …).

Private helpers, test-only symbols, and undocumented underscore-prefixed
names are out of scope for the compatibility checklist. The inventory
script should encode this rule and document exceptions in the checked-in
file header.

**Inventory contents:**

- Public names under the modules above, with constructor signatures and
  defaults.
- Parameter names and default constraints per kernel and likelihood
  (e.g. `rbf.variance`, `rbf.lengthscale`, `Logexp`).
- Model-level behaviours users depend on: `optimize()` (default optimiser
  and options), `optimize_restarts`, `predict` / `predict_quantiles` /
  `posterior_samples_f` return shapes, `print(m)` table layout, regex
  indexing `m['.*lengthscale']`, `constrain_*` / `fix` / `set_prior`,
  `to_dict` / `save` / `load`.

Generated by a script (`scripts/api_inventory.py`) into a checked-in file,
with a CI job that diffs it so API changes are visible in review. The
inventory is also the checklist for the successor compatibility layer.

Supplement with Discussion #1297: which models, kernels and features do
you actually use, and do you maintain custom kernels or likelihoods?

### Workstream C — Golden-value corpus

A set of canonical models with fixed data and seeds, and recorded outputs:
log-likelihood and gradient at fixed parameters, optimised parameters,
predictions (mean, variance, quantiles) at fixed test points.

**Parity claim (decide at Accept):** mathematical agreement within stated
tolerances — not bit-identity across BLAS / JAX. Split each case into:

- **Value parity** at fixed parameters (LL, gradients, predict).
- **Optimise parity** where useful (comparable LL / parameters within
  looser tolerances), recorded separately so platform noise does not fail
  the fixed-parameter oracle.

Platform and dependency versions (NumPy, SciPy, BLAS) are stored in the
JSON metadata next to each artefact.

**First pass (readiness bar — ship in CIP-0010):**

- `GPRegression`: RBF ± ARD, one Matérn, one sum or product
- One sparse regression model
- One classification path (Laplace *or* EP — Discussion may prefer one)
- One latent-variable model (`BayesianGPLVM` or simpler GPLVM)

**Expansion (backlog after readiness bar; builds on CIP-0009 / CIP-000D):**

`SVGP`, `MRD`, `GPCoregionalizedRegression`, the other classification
path, one state-space model, additional non-Gaussian likelihoods.

- In GPy1 the corpus is a regression suite: refactors from CIP-000E/000F
  must not move these numbers beyond stated tolerances.
- For the successor it is the parity suite: the upgrade claim is "these
  numbers match within tolerance".
- Stored as small `.npz` plus JSON metadata (tolerances, GPy version,
  NumPy/SciPy versions).

### Workstream D — Serialisation as the migration path

A successor cannot be assumed to unpickle GPy1 objects. The migration path
for saved models is `to_dict` (JSON), which today is implemented in 9
model/core modules.

- **Readiness bar:** `to_dict` / `from_dict` for every model in the
  **first-pass corpus**, schema version frozen.
- **After bar:** extend to every inventory model, or explicitly mark
  unsupported in the inventory.
- Document "convert your pickles under GPy1: `GPy.load` → `m.to_dict()` →
  file".
- Version the JSON schema so a successor `from_gpy1()` loader has a
  stable target.

### Workstream E — Forward-compatible numerical habits

- **Pure numerical functions** for kernels and likelihoods: CIP-000F
  Stage 2. These become successor port targets and the pattern
  custom-kernel authors look for.
- **Custom-kernel helper (elevated — resolve at Accept):** a GPy1 base
  class (or helper) where authors implement only `K` / `Kdiag`; GPy1
  obtains gradients by finite differences (or existing autodiff-free
  machinery). Goal: custom kernels written in the shape the successor
  will need, *before* the successor exists. Same idea for likelihoods
  (`logpdf` first) if scope allows.
- **Explicit random number generators:** ~108 direct `np.random.*` calls
  outside tests/examples. Accept an optional `rng`
  (`np.random.Generator`) wherever randomness is used (initialisation,
  restarts, sampling). Maps onto explicit PRNG keys in a functional
  successor.
- **Shape conventions documented:** one page that states GPy's conventions
  (X: N×Q, Y: N×D, multi-output index columns, variance shapes returned
  by `predict`), with shape assertions in tests. Successor adopts the
  same conventions so scripts keep working.
- **No new hand-coded-gradient-only features:** new kernels and
  likelihoods should implement the pure forward function first; hand
  gradients are added for GPy1 only.

Optional GPy1 APIs shaped like a successor posterior protocol
(`posterior(X)` with mean / variance / sample) are **open question 4** —
not required for the readiness bar.

### Workstream F — Migration documentation (started in GPy1)

- `docs/migration/` skeleton: what is deprecated and why, how to convert
  saved models, how a custom kernel looks as pure `K`/`Kdiag` functions.
- Grows as Workstreams A–E land; becomes the successor migration guide.

### Non-goals

- Choosing the successor's frameworks, module system or package layout
  (separate GPy2 CIP; Appendix A records inputs).
- Introducing JAX or any autodiff dependency into GPy1.
- Removing working user-facing features during 1.x.
- Re-deciding questions owned by CIP-000E, CIP-000F, CIP-0002, CIP-000B or
  CIP-000D; this CIP only records how their outcomes feed readiness.
- Waiting for full Cython / paramz retirement before marking this CIP
  Implemented.

### Alternatives considered

| Option | Verdict |
|---|---|
| Umbrella readiness CIP coordinating existing CIPs (this CIP) | Preferred |
| Fold everything into a single GPy2 design CIP | Mixes GPy1 maintenance with undecided successor design; blocks useful GPy1 work on design debates |
| Separate CIP per workstream only | Loses the shared frame; deprecation policy and upgrade contract need one owner |
| Start the successor without GPy1 preparation | No parity oracle, no migration format, users surprised by dropped features |

   CIP with this CIP's inventory, corpus and schema as acceptance tests.
   Corpus expansion and remaining inventory serialisation stay as
   backlog.

Backlog tasks are created per workstream after Accept.

## Backward Compatibility

- No working user-facing feature is removed during 1.x; deprecated
  features warn with `FutureWarning`.
- Removing the global `DeprecationWarning` filter will make some warnings
  visible that were hidden (GPy's and other libraries'). Release notes
  should say so; narrow filters ship in the same PR for known noise.
- Adding optional `rng` arguments is backward compatible (default keeps
  current behaviour).
- Dead-code removal (`scipy.weave`) changes no behaviour, because the
  code cannot run.

## Testing Strategy

- Tests that each deprecated entry point emits `FutureWarning` once, with
  the documented message.
- Golden corpus in CI on the supported Python/NumPy matrix, with explicit
  tolerances (value parity vs optimise parity separated).
- API inventory diff in CI; intentional changes update the checked-in
  file in the same PR.
- `to_dict` → `from_dict` round-trip tests for every first-pass corpus
  model (then inventory expansion).
- Full `GPy/testing` suite green at every step.

## Open questions (resolve at Accept)

1. **Successor import name.** Separate name is assumed; which one
   (`gpy2`, `GPy2`, other)? Should GPy1 eventually re-export or redirect?
2. **Deprecation window.** How many GPy1 minor releases must a
   deprecation ship in before the successor's first stable release?
   (See REQ-0003.)
3. **Candidate list.** Which of MPI, GPU, `mcmc`, `datasets` do people
   still use? Anything missing from the list?
4. **Forward-compatible APIs in GPy1.** Should GPy1 gain any successor-
   shaped interfaces now (e.g. a `posterior(X)` object with mean,
   variance and sampling), or keep GPy1's API frozen and add those only
   in the successor? (Not required for the readiness bar.)
5. **Golden corpus tolerances.** Fixed absolute/relative vs per model?
   How are platform-dependent BLAS differences handled in metadata?
   Default proposal: per-model tolerances; value parity strict;
   optimise parity looser.
6. **Custom kernels (elevated).** Provide a GPy1 helper where users write
   only `K`/`Kdiag` and gradients come from finite differences in GPy1,
   so custom kernels are written successor-style before the successor
   exists?

## Appendix A — Design lessons recorded for the GPy2 CIP

Collected from other GP packages (2026-11). Not decided here; listed with
whether GPy1 can act now.

| Lesson | Source | Act in GPy1 now? |
|---|---|---|
| Keep the parameter layer independent of any module framework; tag parameters by support and map tags to bijectors separately | GPJax (moved to Flax NNX in v0.9; current docs describe Paramax) | Partly: CIP-000F Stage 4 Option B |
| Kernel matrices as structured linear operators (Kronecker, low-rank + diagonal, iterative solves) | GPyTorch `linear_operator`; CoLA (JAX) | No; GPy2 design |
| Separate the GP, its finite projection, the approximation and the posterior; posterior is itself a GP | AbstractGPs.jl | No; GPy2 internals behind GPy's model classes |
| Minimal posterior protocol (mean, variance, sample with explicit key); pathwise sampling | BoTorch | Optional (open question 4) |
| Shape annotations and checks from day one | GPflow `check_shapes`; GPJax JIT-safe assertions | Yes: Workstream E shape conventions |
| State-space kernels declare their SDE form; pure-JAX quasiseparable solvers | tinygp | Partly: GPy's `sde_*` kernels already carry this |
| Functional core with a stateful user-facing layer | tinygp's trade-offs vs george | No; GPy2 compatibility layer |
| Clear package boundaries (kernels, likelihoods, approximations, temporal) | JuliaGPs ecosystem | Partly: deprecations reduce the surface |
| Variational parameterisation that admits natural gradients | GPJax | No; GPy2 design |
| JIT compile latency must not make small interactive models slow | (GPy-specific risk) | Record small-N benchmarks in the golden corpus |
