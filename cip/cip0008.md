# CIP-0008: Classic main-branch release pipeline

## Status

- [x] Proposed - Initial idea documented (open for Discussion feedback)
- [x] Accepted - Approved, ready to start work
- [x] In Progress - Actively being implemented
- [ ] Implemented - Work complete, awaiting verification
- [ ] Closed - Verified and complete
- [ ] Rejected - Will not be implemented
- [ ] Deferred - Postponed

## Summary

Replace the current release shape (tests on several long-lived branches;
wheels and PyPI upload only when a GitHub **Release** object is created) with a
**classic main-centric pipeline**: integrate on **`main`**, publish a GitHub
Release on a `vX.Y.Z` tag, CI builds all platform wheels (including Linux
aarch64), then publishes to PyPI. Add a **dry-run** that builds those wheels
without uploading.

**Accepted 2026-10-24** after GPy 1.15.0 used the old GitHub Release path
([Discussion #1228](https://github.com/SheffieldML/GPy/discussions/1228)).
Do not rewrite the live 1.15.0 deploy job; implement on `main` after that
upload finishes.

## Motivation

Today (`.github/workflows/test-and-deploy.yml`):

- `push` to `main` / `devel` / `deploy` runs the test matrix.
- Wheel builds (`build`, `build-linux`) and `deploy` (twine → PyPI) run **only**
  when `github.event_name == 'release'`.
- `workflow_dispatch` cannot dry-run wheel production; aarch64 / manylinux
  artifacts are only proven when someone publishes a Release (#1209).
- Branch roles (`devel` vs `main` vs `deploy`) are easy to misread for new
  maintainers and for automation (Dependabot, branch protection, “default
  branch” expectations).

That works, but it is not the usual open-source release loop and it makes
preflight of Cython wheels (especially new aarch64) awkward. We want a pipeline
that key developers recognise and can operate confidently for the next cut.

## Detailed Description

### Goals

1. **One integration line** — default branch **`main`** (rename `devel`).
2. **Release-published wheels** — publishing a GitHub Release whose tag is
   `vX.Y.Z` on `main` triggers: full tests → build wheels for Linux x86_64 +
   aarch64, macOS, Windows → upload to PyPI (Trusted Publishing / OIDC).
3. **Dry-run without publishing** — `workflow_dispatch` (and/or PRs labelled
   `build-wheels`) runs the same wheel jobs and uploads artifacts to the
   Actions run **without** twine upload, so aarch64 and friends can be verified
   before the real release.
4. **Readable docs** — README / CONTRIBUTING (or CIP compression later): how to
   cut a release in ≤5 steps; what each branch is for if more than one remains.
5. **No behaviour change for `pip install gpy` users** — same project name,
   versioning, and extras (`gpy[plotting]`, etc.).

### Non-goals (this CIP)

- Changing Poetry / Cython build mechanics (CIP-0003).
- Feature work or further issue triage (CIP-0007 trackers).
- Mandatory TestPyPI (optional enhancement if Discussion wants it).

### Accepted target shape

```text
  PRs → main
           │
           ├─ push / PR: test + lint (every commit)
           ├─ workflow_dispatch: build wheels → artifacts only (no PyPI)
           └─ GitHub Release published on tag vX.Y.Z:
                test + build all wheels → twine/Trusted Publishing → PyPI
```

Keep **authoring the GitHub Release by hand** (title and notes), as for 1.15.0.
Do not auto-create Release notes from the tag job in this CIP. Trigger must be
`on.release.types: [published]` only — `on: release` without types queued
**three** copies of `Test Python Lib` for v1.15.0.

GPy is not lynguine: keep the Cython wheel matrix (Windows, macOS, manylinux
x86_64 and aarch64). Take lynguine’s *shape* (default `main`, version-tag
check, `environment` for publish), not a single Ubuntu `poetry publish` job.

### Decisions (open questions, 2026-10-24)

1. **Primary branch:** **`main`**. Rename default `devel` → `main` (there is no
   `main` today). GitHub redirects old `devel` URLs; open PRs retarget.
2. **Retire `deploy`:** **yes**. Last commit July 2024 (1.13.2). Drop it from
   CI triggers; leave the branch for a while, then delete.
3. **Who can publish:** maintainers who can publish a GitHub Release on `main`.
   Add a GitHub Actions **environment** (`pypi` or `release`) for the upload
   job. Prefer **Trusted Publishing** (`pypa/gh-action-pypi-publish` + OIDC);
   GPy already sets `id-token: write` but still uses `twine` + `TWINE_*`.
4. **TestPyPI:** **not required** for this CIP. Optional later. The dispatch
   dry-run is the preflight for aarch64 / manylinux.
5. **Version source of truth:** `pyproject.toml` via Poetry. CI fails the
   publish job unless the Release tag is `v$(poetry version -s)`.

### Out of scope here (do not block Accept)

- Merging #1242 (Python ≥3.11). That waits until 1.15.0 is on PyPI
  ([Discussion #1207](https://github.com/SheffieldML/GPy/discussions/1207)).
- Dependabot PRs #1236–#1241; retarget them at `main` after the rename.

## Implementation Plan

1. **Accepted (this phase):** record decisions; wait until v1.15.0 **deploy**
   is green (or wheels uploaded by hand) before changing the live workflow.
2. **README:** replace “PR `devel` → `deploy`” with: merge to `main`, tag
   `vX.Y.Z`, publish a GitHub Release.
3. **CI:** `push`/`pull_request` on `main` only; split wheel build from
   publish; `workflow_dispatch` dry-run; `release.types: [published]`;
   tag == Poetry version; Trusted Publishing + environment; keep aarch64
   (#1209).
4. **Branch policy:** rename default `devel` → `main`; Dependabot
   `target-branch: main`; drop `deploy` from triggers.
5. **First release on the new path** (after 1.15.0): checklist; close CIP.

## Backward Compatibility

- End users: unchanged `pip install gpy` story.
- Contributors: PRs target **`main`** after the rename. Document in README.
- Maintainers: still publish a GitHub Release (same 1.15.0 click path). The
  `devel` → `deploy` PR is retired; `on: release` without `types` is retired.

## Testing Strategy

- Dry-run `workflow_dispatch` produces manylinux x86_64 + aarch64, macOS, and
  Windows wheel artifacts with Cython extensions present (`auditwheel` /
  `delocate` / smoke-import as today).
- Tag on a throwaway or pre-release version hits PyPI Test (if enabled) or a
  private check before production.
- Regression: existing test matrix stays green on the primary branch.
