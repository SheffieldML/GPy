# CIP-0011: Integrate numerical stability suite (separate from unit tests) with cross-branch comparison

## Status

- [x] Proposed - Initial idea documented
- [x] Accepted - Approved, ready to start work
- [x] In Progress - Actively being implemented
- [x] Implemented - Work complete, awaiting verification
- [ ] Closed - Verified and complete
- [ ] Rejected - Will not be implemented
- [ ] Deferred - Postponed

## Summary

Land the numerical stability suite currently at the repo root
(`test_numerical_stability.py`) as a **first-class, separate track** from
`GPy/testing` unit tests. Wire optional CI, and add a **cross-branch
comparison runner** so a candidate branch can be scored against a baseline
(same tests, two installs).

Known defects stay as `xfail(strict=True)` until CIP-0012 removes them.

## Motivation

Unit tests in `GPy/testing` check API shape, gradients on ordinary data, and
smoke paths. They do not systematically probe overflow, cancellation, extreme
conditioning, or translation invariance. Claude's suite found **11 real
defects** (debugger breakpoints on NaN paths, Gamma overflow, stationary
kernel cancellation under large offsets, Bernoulli clipping, etc.) that the
existing suite never hit.

If we drop that file into `GPy/testing` without policy:

1. Default CI (`pytest GPy/testing`) grows by design with ~20 expected
   failures — noisy and easy to misread.
2. Fix PRs and regression PRs share one green/red signal; we lose a clear
   "numerics improved vs baseline" story.
3. There is no way to ask: *does this branch fix more xfails than `main`
   without introducing new failures?*

CIP-0009 / CIP-000A / CIP-0010 already talk about coverage, tiered CI, and a
golden-value corpus. This CIP adds a **behavioural numerics gate** that is
orthogonal to those: finiteness, accuracy vs scipy, and invariances under
extreme but representable inputs.

## Detailed Description

### Goals

1. **Separate suite location** — not mixed into the default unit-test
   invocation used by `.github/workflows/test-and-deploy.yml`.
2. **Stable contracts** — finiteness, accuracy (conditioned tolerances),
   invariance (translation / rescaling); known bugs marked
   `xfail(strict=True)` with cause strings (already in the draft file).
3. **Cross-branch comparison** — run the *same* suite against two installed
   trees (baseline vs candidate) and report improvements / regressions.
4. **Optional CI** — do not block the PR canary on the full matrix of known
   xfails; provide a dedicated job or workflow that still surfaces
   unexpected failures and XPASS.

### Non-goals

- Fixing the defects (CIP-0012).
- Replacing CIP-0010's golden-value corpus (fixed seeds / recorded outputs
  for upgrade parity). This suite is adversarial / extreme-input, not a
  golden dump.
- Making numerical jobs part of the 3×4 publish matrix by default.

### Layout (recommended)

Mirror `benchmarks/` as a sibling top-level track:

```text
numerical_stability/
  README.md
  test_numerical_stability.py   # moved from repo root
  compare.py                    # or scripts/compare_numerical_stability.py
  conftest.py                   # markers, shared fixtures if needed
```

**Why not `GPy/testing/`?**

- Default CI already runs `uv run pytest GPy/testing`. Keeping numerics
  outside that path needs no `-m` discipline from every contributor.
- CIP-000A path filters can treat `numerical_stability/` as its own
  "code" class without pulling every docs PR into a long job.
- Parallel to `benchmarks/regression/`: specialised evaluation, not unit
  correctness of every public method.

**Alternative (acceptable if Accept prefers):** keep the file under
`GPy/testing/` with `@pytest.mark.numerical`, and change the default
workflow to `pytest GPy/testing -m "not numerical"`. Slightly more
convenient for `pytest --pyargs GPy`, but easier to accidentally include.

### Pytest policy

| Outcome today | Meaning |
|---------------|---------|
| `passed` | Contract holds on this install |
| `xfailed` (strict) | Known defect; expected |
| `XPASS` | Known defect fixed — **fail the job** until the marker is removed (CIP-0012 chore) |
| `failed` / `error` | Unexpected regression — fail |
| `skipped` | Optional dependency (e.g. SVGP / `climin`) |

Register marker in `pyproject.toml`:

```toml
[tool.pytest.ini_options]
markers = [
  "numerical: adversarial / extreme-input numerical stability (CIP-0011)",
]
```

### How to run (local)

```bash
# Unit tests only (unchanged)
uv run pytest GPy/testing

# Numerical suite only
uv run pytest numerical_stability/ -q

# Both
uv run pytest GPy/testing numerical_stability/
```

### Cross-branch comparison

**Problem.** pytest alone compares one install to hard-coded oracles. We
need: *same suite source → two codebases → outcome diff*.

**Design.**

```text
                    ┌─────────────────────────────┐
   suite source ───▶│  numerical_stability/*.py   │  (one tree: baseline,
                    │  (fixed path or git ref)     │   candidate, or PATH)
                    └─────────────┬───────────────┘
                                  │
              ┌───────────────────┴───────────────────┐
              ▼                                       ▼
     install baseline                          install candidate
     (worktree / venv A)                       (worktree / venv B)
              │                                       │
              ▼                                       ▼
        pytest --json-report                   pytest --json-report
              │                                       │
              └───────────────────┬───────────────────┘
                                  ▼
                         compare nodeids
                         write report.md + exit code
```

**CLI sketch** (name flexible; live under `numerical_stability/compare.py`
or `scripts/compare_numerical_stability.py`):

```bash
uv run python numerical_stability/compare.py \
  --baseline main \
  --candidate HEAD \
  --suite-from baseline \
  --report numerical_stability/last-compare.md
```

| Flag | Role |
|------|------|
| `--baseline REF` | Git ref for code under test A (default: `origin/main`) |
| `--candidate REF` | Git ref for code under test B (default: `HEAD`) |
| `--suite-from {baseline,candidate,PATH}` | Which copy of the *tests* to run against both installs. Default: **`baseline`** once merged to `main`, so candidates cannot weaken assertions and call it an improvement. Before merge, use `PATH` to the draft file. |
| `--work-dir DIR` | Scratch for worktrees + venvs |
| `--report PATH` | Markdown summary |

**Outcome matrix (per test nodeid):**

| Baseline | Candidate | Classification |
|----------|-----------|----------------|
| xfailed | passed / XPASS | **improvement** |
| passed | failed / error | **regression** (fail compare) |
| xfailed | failed (not xfail) | **regression** (fail compare) |
| passed | passed | stable |
| xfailed | xfailed | known debt |
| skipped | skipped | ignore |
| absent ↔ present | **suite drift** (warn; fail if `--strict-suite`) |

**Exit code:** non-zero iff any regression (or strict suite drift).
Improvements alone → 0, listed at the top of the report.

**Implementation notes.**

1. Prefer `git worktree add` for each ref over stash juggling.
2. Build/install each worktree with `uv sync` into an isolated venv
   (Cython extensions must match that tree).
3. Invoke pytest with `PYTHONPATH` / `uv run --directory <worktree>` so
   imports resolve to the tree under test, while the suite file is
   always the `--suite-from` copy (copied or mounted read-only into the
   run).
4. Prefer `pytest-json-report` or JUnit XML for machine-readable
   outcomes; fall back to parsing `--report-log` if we want zero new
   deps (Accept choice).
5. Do **not** compare floating-point dumps between branches here; that
   is CIP-0010 golden corpus territory. This compare is **pass/xfail
   outcome** based (optionally extend later with recorded metrics).

### CI integration

Minimal viable (after Accept):

1. **Workflow job `numerical-stability`** on `pull_request` / `push` to
   `main` when paths touch `GPy/` or `numerical_stability/`:
   - Ubuntu, Python 3.12 (one cell — numerics are not OS-matrix drama).
   - `uv run pytest numerical_stability/ -q`
   - Job fails on unexpected failures and on **XPASS** (strict xfail).
2. **Optional `workflow_dispatch` / nightly:** run
   `compare.py --baseline origin/main --candidate HEAD` on the PR head
   and upload the markdown report as an artifact (and optionally a PR
   comment).

Align with CIP-000A: this job is separate from the PR canary; docs-only
PRs skip it via path filters.

## Implementation Plan

1. **House the suite**
   - Create `numerical_stability/` (+ short README: how to run, markers, link to CIP-0011/0012).
   - Move `test_numerical_stability.py` from repo root; add
     `@pytest.mark.numerical` on modules or via `pytestmark`.
   - Register the marker in `pyproject.toml`.

2. **Keep unit CI unchanged**
   - Confirm `.github/workflows/test-and-deploy.yml` still only runs
     `pytest GPy/testing`.
   - Add a dedicated `numerical-stability` job (path-filtered).

3. **Cross-branch runner**
   - Implement `compare.py` with worktrees, dual installs, outcome diff,
     markdown report, non-zero exit on regression.
   - Document examples in `numerical_stability/README.md`.

4. **Smoke validation**
   - On current `main` install: suite green modulo strict xfails (~3s locally).
   - `compare.py --baseline <same> --candidate <same>` → empty diff, exit 0.
   - Synthetic check: temporarily remove one xfail on a still-broken
     path → compare against true baseline reports regression.

5. **Handoff to CIP-0012**
   - Freeze the defect list in CIP-0012 Implementation Status.
   - Policy: any XPASS on `main` is a CIP-0012 checklist item (remove
     marker in the same PR as the fix).

## Backward Compatibility

- No public API change.
- Contributors who only run `pytest GPy/testing` see no difference.
- Optional new dev dependency only if we adopt `pytest-json-report`
  (otherwise parse JUnit / report-log).

## Testing Strategy

- Self-test the suite on `main` (expected xfail set stable).
- Compare runner unit tests with fixture JSON reports (no need to build
  two full GPy trees in unit CI).
- One integration smoke in CI or a documented manual recipe using two
  worktrees.
