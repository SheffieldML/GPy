## Summary

Migrate GPy's packaging and CI from a `setup.py`-centric workflow to
[Poetry](https://python-poetry.org/), with a PEP 517-style `pyproject.toml`, a
committed `poetry.lock`, a Poetry build hook for Cython extensions
(`build_extension.py`), and workflows that install and test via `poetry install` /
`poetry run pytest`.

The work exists as an open PR against `devel`. It never merged. This CIP captures
the intent, what landed in the branch, what blocked merge, and where the proposal
has drifted from today's packaging reality.

## Motivation

By mid-2024, dependency and PEP-related issues were stacking: NumPy / Matplotlib
compatibility reports, Cython extension builds, and inconsistent developer install
paths. Martin's stated goal was better dependency tracking and clearer
communication of compatible version ranges for contributors and CI.

Related open or adjacent work at the time (and still relevant):

- [#1000](https://github.com/SheffieldML/GPy/pull/1000) — pep508 dependency specification
- [#975](https://github.com/SheffieldML/GPy/pull/975) — oldest-supported-numpy for build
- [#1031](https://github.com/SheffieldML/GPy/pull/1031) — Cython as setup-time, not runtime, dependency
- [#1006](https://github.com/SheffieldML/GPy/pull/1006) (merged) — partial move of metadata into PEP 621 `pyproject.toml`

## Detailed Description

### What PR #1080 actually changed

| Area | Change |
|------|--------|
| Metadata / deps | New Poetry `[tool.poetry]` `pyproject.toml` (version pinned to `1.13.1` at the time) |
| Lockfile | Added `poetry.lock` (~3.3k lines) |
| Extensions | Extracted Cython `Extension` definitions into `build_extension.py` with Poetry `build()` hook; renamed away from `build.py` after macOS name clashes |
| CI | Rewrote `.github/workflows/test-and-deploy.yml` to use `pip install poetry` then `poetry install` / `poetry build` |
| Docs | README notes the Poetry switch; shortens some install narrative |
| Tests | Small import fix in `test_gpy_kernels_state_space.py` |
| Left in place | Existing `setup.py` / `setup.cfg` still present on the branch (dual packaging surface) |

### Declared dependency policy in the PR

- Python `>=3.9,<4`
- NumPy `>=1.7,<2` — explicit upper bound because **paramz was incompatible with NumPy 2**
- SciPy version markers for Python 3.9 vs newer
- Cython listed under runtime Poetry dependencies
- `tables >= 3.9.0` as a hard dependency (broader than historical `setup.py` core deps)
- Optional extras aligned with prior docs / notebook / plotting / mpi groupings
- Dev group: matplotlib, pytest, pods

### Build / CI design

- Build backend: `poetry.core.masonry.api`
- Build-system requires: `poetry-core`, `setuptools`, `wheel`, `numpy`, `cython` (no SciPy in the isolated build env)
- macOS test matrix dropped Python 3.9 (SciPy install issues noted in workflow comments)
- Linux release wheels still used manylinux + auditwheel
- Artifact upload used `actions/upload-artifact@v3`; Linux job still used `actions/checkout@v1`

### Known blocker at the time (author comment, 2024-07-29)

Apple Silicon (M-series) CI failed; Intel Mac could not reproduce. Martin offered three options:

1. Drop macOS support temporarily
2. Obtain Apple Silicon runners / hardware for debugging
3. Stick with `setup.py` for now

No maintainer decision was recorded on the PR. No reviews were filed. The PR
status is now **CONFLICTING** with `devel`.

### Drift versus current `devel` (as of 2026-10)

These gaps are the main reason a blind merge is unsafe:

1. **NumPy policy reversed.** Current `devel` builds against `numpy>=2` (setuptools
   PEP 517 `pyproject.toml` and CI). The Poetry PR freezes NumPy `<2`. Merging
   as-is would undo NumPy 2 support.

2. **Package / version identity.** Poetry metadata uses name `GPy` and version
   `1.13.1`. Current `devel` normalizes the distribution name to `gpy` and ships
   `1.14.2`. Artifact naming and PyPI identity need a single policy.

3. **SciPy in the build environment.** Current `devel` documents that
   `choleskies_cython.pyx` cimports `scipy.linalg.cython_blas` and therefore
   requires SciPy in the isolated build env. The Poetry PR's
   `[build-system].requires` omits SciPy.

4. **Cython dependency class.** Poetry lists Cython as a project dependency.
   [#1031](https://github.com/SheffieldML/GPy/pull/1031) argues it belongs in
   build requirements only. The CIP should pick one story.

5. **`tables` as a hard dependency.** That widens the install footprint relative
   to historical core `install_requires` (`numpy`, `six`, `paramz`, `scipy`).
   Needs an explicit product decision.

6. **Dual packaging retained.** Leaving `setup.py` beside Poetry without a
   deprecation plan invites two sources of truth for extras and extension builds.

7. **CI toolchain age.** Current `devel` tests Python 3.11–3.14 with setuptools
   editable installs and `upload-artifact@v4`. The Poetry branch targets 3.9–3.12
   and older actions.

8. **Apple Silicon unresolved.** `macos-latest` runners are Apple Silicon today.
   The original blocker is more, not less, relevant.

9. **Lockfile maintenance.** A committed `poetry.lock` for a library (vs an
   application) is contentious: it helps reproducible contributor installs but
   can fight downstream solvers. The CIP must state whether GPy locks for apps
   or only pins ranges for a library.

10. **Stale merge base.** Two years of `devel` packaging and CI work would need
    rebasing before any revive.

### Design alternatives (for community decision)

| Option | Idea | Upside | Downside |
|--------|------|--------|----------|
| A | Revive Poetry: rebase #1080, fix NumPy 2 / SciPy build / name / CI | Uses existing contributor work; lockfile for contributor envs | Rebase cost; Poetry + Cython + wheels still awkward; library lockfile debate |
| B | Keep setuptools PEP 517 (current `devel` direction); take only portable ideas from #1080 | Lowest churn; already shipping NumPy 2 wheels | Leaves Poetry migration unfinished; contributors who wanted Poetry stay unsatisfied |
| C | Modernize with another tool (hatchling / scikit-build-core / meson-python) | Stronger native-extension story in 2026 | New migration; discards most of #1080's Poetry-specific work |
| D | Hybrid: `pyproject.toml` metadata + setuptools backend; optional Poetry only for contributors | Smaller decision; can absorb #1000 / #1031 | Still two mental models unless documented carefully |

**Portable wins from Martin's work regardless of option:**

- Centralize Cython `Extension` definitions outside a monolithic `setup.py`
- Make contributor install / test commands explicit in README and CI
- Encode NumPy / SciPy / Python compatibility as machine-readable constraints
- Treat Apple Silicon as a first-class CI target, not an afterthought

## Implementation Plan

Retrospective path (proposed):

1. **Decide packaging strategy (A/B/C/D)** with maintainers and Martin if available.
2. **If A (Poetry):** rebase onto current `devel`; update version and distribution name; lift NumPy pin in line with paramz status; add SciPy to build-system requires; move Cython to build-only; revisit `tables`; refresh Actions; prove green on Apple Silicon.
3. **If B or D:** close or supersede #1080; open follow-up tasks to extract `build_extension.py`-style extension config and pep508 metadata without Poetry.
4. **If C:** reject #1080 with pointer to a new CIP for the chosen backend.
5. **Document the install story** for end users (`pip install gpy`) vs contributors (editable / poetry / hatch) so README and CI cannot diverge again.
6. **Resolve or explicitly defer** related PRs #1000, #975, #1031 under the chosen option so packaging PRs stop stacking without a design owner.

## Backward Compatibility

- **End users installing from PyPI** should keep using `pip install gpy` with wheels; a Poetry migration must not require Poetry at runtime.
- **Contributors** would need Poetry (option A) or continue with editable setuptools installs (B/D).
- **Dependency tightening** (NumPy `<2`, hard `tables`) is a compatibility break relative to current `devel` and must not ship without release notes and CI proof.
- **Distribution name** must stay consistent with the PyPI project (`gpy` / `GPy` normalization policy already fought on `devel`).

## Testing Strategy

- Matrix: Linux, Windows, macOS (Apple Silicon), Python versions supported by the chosen policy.
- Prove: `pip install` from built wheel; editable contributor install; `pytest GPy/testing`.
- Prove: Cython extensions import on each platform (`stationary_cython`, `choleskies_cython`, `linalg_cython`, `coregionalize_cython`, `state_space_cython`).
- Prove: isolated PEP 517 build with SciPy present for `cython_blas` cimports.
- Explicit acceptance criterion: **macOS Apple Silicon CI green**, or a written decision to drop / defer that platform (Martin's option 1) recorded in this CIP.

## Flaws and open questions (review checklist)

Use this list when discussing the PR:

1. Is Poetry still the right packaging tool for a Cython-heavy *library* in 2026?
2. Should GPy commit a lockfile, or only declare ranges?
3. How do we support NumPy 2 and paramz together today?
4. Why is `tables` required rather than optional?
5. Why keep `setup.py` after a Poetry migration?
6. Is SciPy correctly declared for isolated builds?
7. Is Cython a runtime dependency or a build dependency?
8. What is the supported macOS story on Apple Silicon?
9. Who owns packaging PRs so #975 / #1000 / #1031 / #1080 stop overlapping?
10. What is the single source of truth for version and distribution name?
