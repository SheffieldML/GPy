# CIP-0008: Classic main-branch release pipeline

## Status

- [x] Proposed - Initial idea documented (open for Discussion feedback)
- [ ] Accepted - Approved, ready to start work
- [ ] In Progress - Actively being implemented
- [ ] Implemented - Work complete, awaiting verification
- [ ] Closed - Verified and complete
- [ ] Rejected - Will not be implemented
- [ ] Deferred - Postponed

## Summary

Replace the current release shape (tests on several long-lived branches;
wheels and PyPI upload only when a GitHub **Release** object is created) with a
**classic main-centric pipeline**: integrate on one primary branch, cut a
version tag, CI builds all platform wheels (including Linux aarch64), then
publishes to PyPI with a dry-run path that does not require a live Release.

Keep this CIP **Proposed** through the next release cycle so maintainers can
adjust the design from Discussion feedback before Accept.

## Motivation

Today (`.github/workflows/test-and-deploy.yml`):

- `push` to `main` / `devel` / `deploy` runs the test matrix.
- Wheel builds (`build`, `build-linux`) and `deploy` (twine → PyPI) run **only**
  when `github.event_name == 'release'`.
- `workflow_dispatch` cannot dry-run wheel production; aarch64 / manylinux
  artifacts are only proven when someone publishes a Release (#1209).
- Branch roles (`devel` vs `main` vs `deploy`) are easy to misread for new
  maintainers and for automation (Dependabot, branch protection, “default
  branch” expectations).

That works, but it is not the usual open-source release loop and it makes
preflight of Cython wheels (especially new aarch64) awkward. We want a pipeline
that key developers recognise and can operate confidently for the next cut.

## Detailed Description

### Goals

1. **One integration line** — document and use a single primary branch for
   merge-ready work (proposal: keep `devel` as default *or* rename/promote
   `main`; decide in Discussion — see open questions).
2. **Tag-driven release** — cutting `vX.Y.Z` (annotated tag) on that line
   triggers: full tests → build wheels for Linux x86_64 + aarch64, macOS,
   Windows → attach artifacts → upload to PyPI (Trusted Publishing / OIDC
   already present).
3. **Dry-run without publishing** — `workflow_dispatch` (and/or PRs labelled
   `build-wheels`) runs the same wheel jobs and uploads artifacts to the
   Actions run **without** twine upload, so aarch64 and friends can be verified
   before the real release.
4. **Readable docs** — README / CONTRIBUTING (or CIP compression later): how to
   cut a release in ≤5 steps; what each branch is for if more than one remains.
5. **No behaviour change for `pip install gpy` users** — same project name,
   versioning, and extras (`gpy[plotting]`, etc.).

### Non-goals (this CIP)

- Changing Poetry / Cython build mechanics (CIP-0003).
- Feature work or further issue triage (CIP-0007 trackers).
- Mandatory TestPyPI (optional enhancement if Discussion wants it).

### Proposed target shape

```text
  PRs → primary branch (devel or main)
           │
           ├─ push: test + lint (every commit)
           ├─ workflow_dispatch / label: build wheels → artifacts only
           └─ tag v*: test + build all wheels → GitHub Release notes → PyPI
```

Open to Discussion: whether GitHub Release notes are auto-created from the tag
job or still authored manually once.

### Open questions (leave CIP Proposed until settled)

1. **Primary branch name:** stay on `devel`, or move default to `main` and
   treat `devel` as legacy?
2. **Retire `deploy`?** Is it still used, or can it be removed from CI triggers?
3. **Who can publish?** Branch protection + environment `pypi` approval vs
   any maintainer with release rights.
4. **Pre-release / TestPyPI?** Optional gate before first aarch64 production
   upload.
5. **Version source of truth:** Poetry `pyproject.toml` only, with tag matching
   `v$(poetry version -s)` enforced in CI?

## Implementation Plan

1. **Community review (this phase):** Discussion tagged to key developers;
   revise this CIP from feedback; **do not Accept until after next release
   feedback window** (or sooner if consensus is clear).
2. **Document current vs target** in CIP + short README “Releasing” section
   (draft under Proposed is fine).
3. **CI:** split “build wheels” from “publish”; allow dispatch dry-run; keep
   release/tag path publishing; ensure aarch64 stays in the matrix (#1209).
4. **Branch policy:** protection rules + default-branch decision; remove stale
   triggers.
5. **First release on the new path:** checklist run; close CIP when verified.

## Backward Compatibility

- End users: unchanged install story.
- Contributors: PR target may change if default branch moves; document in
  README.
- Maintainers: release procedure changes; old “create Release UI first” flow
  may be replaced by “tag → workflow creates/attaches Release”.

## Testing Strategy

- Dry-run `workflow_dispatch` produces manylinux x86_64 + aarch64, macOS, and
  Windows wheel artifacts with Cython extensions present (`auditwheel` /
  `delocate` / smoke-import as today).
- Tag on a throwaway or pre-release version hits PyPI Test (if enabled) or a
  private check before production.
- Regression: existing test matrix stays green on the primary branch.
